Как считает аудит

Движок принимает банковскую отчётность, проверяет её на пригодность, прогоняет каждый банк через восемь статистических тестов и возвращает тех, чьи числа не похожи на возникшие естественным путём. Здесь — логика каждого алгоритма и настоящие цифры, на которых он сработал.

Правило, из которого следует всё остальное

Аудит — это статистический аргумент. Любая тихая починка данных ломает аргумент незаметно, поэтому в движке её нет.

Severity.ERROR Файл не может быть проверен. Задача падает с этим текстом — результата не будет вовсе.
Severity.WARNING Аудит прошёл, но вот что пришлось выбросить или предположить. Показывается рядом с результатом.

Почему так: непрочитанная сумма, тихо ставшая нулём, сдвинула бы гистограмму первых цифр. Строка без имени банка образовала бы фантомный банк с крошечной выборкой — и он автоматически оказался бы «подозрительным». Дубликат раздувает n, то есть сужает ту самую погрешность выборки, ради которой существует порог 300.

Отсюда правило: либо файл отклоняется с причиной, либо проверяется — но с перечнем повреждений рядом.

Проверка данных вживую

Отметьте, что не так с присланным реестром — движок ответит тем же текстом, что увидел бы аудитор. Сообщения настоящие, из ingest/validation.py.

Ни одна из этих ситуаций не отменяет аудит: строки выбрасываются, а факт выбрасывания доезжает до дашборда. Отменяют его только ошибки уровня ERROR — например, если в реестре вообще нет колонки с суммой или после чистки не осталось строк.

Что это за файл

В образце датасета роли заданы именами файлов. Загруженный через дашборд файл называется как угодно, поэтому роль читается по его собственным колонкам.

register  ← есть колонка с id кредита
normativ  ← есть колонки chegara_k1 / lcr / k3
report    ← есть колонка с названием показателя

Порядок проверок важен: и у реестра, и у нормативов есть колонка банка, и у реестра, и у отчёта есть суммы. Каждая роль опознаётся по признаку, который есть только у неё.

Обязательный алгоритм: Бенфорд и MAD

Столбцы — как первая цифра сумм кредитов распределена на самом деле, пунктир — как должна по закону. Выберите банк.

P(d) = log₁₀(1 + 1/d) MAD = (1/9) · Σ |набл(d) − P(d)|

Почему по реестру кредитов. В агрегированном отчёте на банк приходится 78 чисел. Погрешность выборки при таком объёме шире искомого отклонения, и подозрительными вышли бы все банки подряд. В реестре — от 1568 до 2544 записей на банк, и группировка идёт по банку, а не по банк-месяцу: по месяцам вышло бы 246–461, снова ниже порога.

Почему MAD, а не χ². При n около двух тысяч χ² объявляет значимым любое отклонение, включая практически пустяковое, и перестаёт различать банки. Интервалы Нигрини от размера выборки не зависят. χ² всё равно считается — как независимая сверка, и на Aloqa обе метрики согласны.

Семь детекторов

Пять решают вердикт, два только показываются. Нажмите — формула, порог, баллы всех банков и настоящая улика.

Кто на чём сработал

Строка — банк, столбец — тест. Заливка означает срабатывание; серым — тест посчитан, но молчит.

Как складывается вердикт

Ни обучения, ни весов: балл — сумма баллов сработавших решающих тестов.

reason     = имена сработавших решающих тестов, в порядке реестра DETECTORS
composite  = сумма их баллов                 → ключ сортировки
suspicious = len(reason) > 0                 → попадёт ли банк в файл

метрика в файле = MAD, если сработал Бенфорд (её называет ТЗ),
                  иначе наибольший балл среди сработавших

Справочные тесты (last_digit, balance) считаются и показываются, но в reason не входят: они срабатывают только на банках, уже пойманных решающими тестами, и не добавили бы ни одного нового.

Путь загруженного файла

Аудит по полному реестру занимает секунды и грузит процессор, поэтому в запросе он не выполняется.

app/submissions/ — model · queue · runner · repository · service

Воркер один намеренно: два параллельных аудита в одном интерпретаторе конкурируют за GIL и не заканчиваются быстрее, зато последовательная очередь даёт аудитору осмысленный номер в очереди. Это обычный поток, а не asyncio-задача, потому что работа блокирующая.
